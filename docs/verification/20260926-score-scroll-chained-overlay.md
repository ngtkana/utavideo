# 2026-09-26 楽譜スクロール表示（issue #142）の実装時の検証記録

issue #142（`overlay` を `enable=between(t,...)` でチェーンする方式）の設計自体は issue のコメント
（設計段階の検証）で確認済み。実装（`graph.score_scroll_filter`）を書く過程で、追加の不具合を
1件見つけたので記録する。

## 環境

- macOS、ffmpeg 9.0.2

## 見つけた不具合：画像入力に前処理フィルタを挟んでからチェーンにファンアウトすると2つ目以降が映らない

チェーンした複数の `overlay` は同じ画像入力（`image_label`）を毎回参照する
（`[score0][1:v]overlay=...`, `[score1][1:v]overlay=...`, ...）。この`image_label`に生の入力
参照（`1:v` など）を渡す分には問題なく動く。

ところが、検証中に一度 `[1:v]format=rgb24[ov0]` のように**フィルタを1回だけ通した出力**を
`image_label`として複数の`overlay`にファンアウトしたところ、**2つ目以降のチェーンで画像が
描かれず、背景だけが見える**という不具合が再現した（1つ目のチェーンだけは正しく描かれる）。

切り分けのため、同じ画像を使って次の組み合わせを試した。

| 背景側に`format=rgb24`を通す | 画像側に`format=rgb24`を通す | 結果 |
|---|---|---|
| 通さない | 通さない | 正常（軽微な圧縮由来のノイズのみ） |
| 通す | 通さない | 正常（軽微な圧縮由来のノイズのみ） |
| 通さない | 通す | **2つ目以降のチェーンで画像が消える** |

**画像側**にフィルタを1回だけ通した出力を複数の`overlay`にファンアウトしたときだけ再現した。
原因はffmpeg側の挙動として不明（`split`フィルタで明示的に複製すれば起きないと推測されるが未検証）。

## 対処

`score_scroll_filter`は`image_label`をそのまま複数回の`overlay`に埋め込むだけの実装にし、
**呼び出し側が`image_label`に前処理済みのフィルタ出力を渡さないこと**を関数のdocstringに注記した。
実際の用途（横1段の楽譜PNGをそのまま重ねる）では画像側に前処理は不要なため、この制約が問題に
なることはない想定。将来、画像に前処理（スケーリング等）が必要になったら、`split`フィルタで
チャンクの数だけ複製してから個別に渡す設計にする。

## 見つけた不具合：note_events() のx座標が実際のピクセル幅の約25倍になっていた（issue #141のバグ）

実際の楽譜（121小節）で `score_scroll_filter` を通しで確認したところ、最初の80音符ぶん
（曲の最初の約18%の時間）だけで、譜面画像の右端（15372px）をはるかに超えるx座標
（約69000px）に達し、それ以降は画像の範囲外を指すため何も描かれない（背景だけが見える）
ことが分かった。

原因は `note_events()`（issue #141）の実装にあった。Verovioが書き出すSVGは、外側の`<svg>`が
実際のピクセル数（`width="15372px"`）を持つのに対し、bboxの座標が書かれているのは**内側の
`<svg class="definition-scale">`要素のviewBox**（Verovioの内部単位。例:`viewBox="0 0 384290
4230"`）で、両者の縮尺が異なる。実測したところ、viewBox単位とピクセルの比は常に
`1000 / scale`（`scale`は`render_horizontal_svg`・`note_events`に渡すレンダリングの拡大率
オプション、既定40）と一致した。`render_horizontal_svg`が返すSVGを`svg_to_png`でラスタライズ
する分にはresvg-pyがviewBoxを見て正しく縮小するので影響が無いが、bboxの数値を正規表現で
直接読んでいた`note_events()`だけ、この換算を忘れており、viewBox単位のままの値（実際の
ピクセル値の約25倍、scale=40のとき）を返していた。

### 対処

`_parse_note_bboxes`で、bboxのx座標に`scale / 1000`を掛けてからピクセル単位に直すようにした。
回帰テストとして、`note_events()`の最後の点のxが、`render_horizontal_svg`が返すSVGの実際の
ピクセル幅を超えないことを確かめるテストを追加した（このテストは修正前は失敗していたことを
確認済み）。

## 見つけた不具合：overlayにformat=rgbが無いと、YUV420でのブレンドで位置がずれる（レビューで発覚）

`graph.py`の既存`_stack_layers`は、overlayに`format=rgb`を明示している（YUV合成での色ずれを
避けるためとコメントにもある）。`score_scroll_filter`にはこれが漏れていた。

ffmpegの`overlay`フィルタは`format`オプションの既定値が`yuv420`で、指定しない限り主入力・
画像入力の実際のpix_fmtに関わらずYUV420でブレンドされる。x座標をR・G・Bの3バイトに分けて
エンコードした画像（`geq`フィルタで生成）を静止画のoverlayで重ねて実測したところ、
`format=rgb`が無いと一部の座標（例:デコードすると500になるはずの画素）が全く違う値に化けた
（クロマ間引きによる劣化）。`format=rgb`を付けると全て正しくデコードできた。

楽譜の線は細く、`.ass`字幕の合成でRGB合成が必要とされたのと同種の劣化が起きる場所なので、
`score_scroll_filter`のoverlayにも`format=rgb`を追加した。回帰テストとして、上記のRGB3バイト
エンコード画像を使い、チャンクの境界をまたいだ複数地点で画素値が期待するx座標と厳密に一致する
ことを確かめるテストを追加した（`format=rgb`を外すと実際に失敗することを確認済み）。

なお、この節の初版では「ピクセル位置をRGB直接エンコードした画像は、ロスレスでもYUV系の中間
処理を経由すると誤差が出るため検証に向かない」と書いていたが、これは`format=rgb`が無いことに
よる劣化そのものだった。`format=rgb`を付ければ正しく検証に使える。

## 数値的な正しさの再検証

設計段階の検証（cross-correlationでの移動量測定）を実装（`score_scroll_filter`）に対しても
再実施した。可読な縞模様の画像＋実フレームの目視確認、および相互相関による移動量測定（速度が
小さいと縞の周期にエイリアシングして測定自体がぶれることがある）を組み合わせて、チャンクの
継ぎ目をまたいでも動きが滑らかで飛びが無いことを目視で確認した。`format=rgb`修正後は、RGB3バイト
エンコード画像による厳密なピクセル一致の確認もできている（上記参照）。
