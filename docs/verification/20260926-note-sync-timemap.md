# 2026-09-26 音符ごとの発音時刻とx座標の対応づけ（issue #141）の検証記録

`inst` に楽譜を音源に合わせて横スクロール表示する構想（issue #139）で、音符ごとの
「譜面上のx座標」と「発音時刻」を対応づける同期計算（issue #141）にあたっての検証。

## 環境

- macOS、Python 3.12、`verovio` 6.3.0
- 動作確認に使った楽譜: ユーザー提供の実際の .mscz（121小節、テンポ変化・rit.あり）

## Verovioで音符ごとの発音時刻とx座標が取れることの確認

- `toolkit.renderToTimemap()` は、`<sound tempo>` を反映した各音符の発音時刻（`tstamp`、ミリ秒）を、
  音符のIDごとの `on`/`off` イベントの列として返す。テンポ変化（120→60）を含む手作りの楽譜で、
  60bpm区間の四分音符が120bpm区間のちょうど2倍の長さになることを確認した
- `svgBoundingBoxes: true` オプションを付けてSVGを書き出すと、`<g id="bbox-<音符ID>" class="note
  bounding-box"><rect x=... width=... /></g>` という形で、音符ごとの画面上のx座標（bbox）が
  埋め込まれる
- 上記2つは同じ音符IDで対応づけられるため、IDをキーに突き合わせて (x, t) の点列を作れる
- 和音（同時に鳴る複数の音符）は `on` イベントの発音時刻が完全に一致し、bboxのxもほぼ同じ値になる
  ことを確認した（1つの点にまとめて扱う）
- 休符には発音時刻が無い（`on` イベントが無い）ため、前後の音符を結ぶ直線で近似することになる

`getElementAttr()` という別のAPIも試したが、期待した座標を返さなかった（`Element ... not found`
の警告が出る）。`svgBoundingBoxes` によるSVG内のbbox要素を直接パースする方法で代用した。

## rit.の扱い

実データのMusicXMLを調べたところ、`rit.`は次のように**自由テキスト**としてしか入っていなかった。

```xml
<direction-type><words>rit.</words></direction-type>
```

この文字列自体はプログラムから意味を読み取れない。ただし、同じ実データでは `rit.` の近くに
`<sound tempo="262.5"/>` という**実効テンポの数値**も一緒に書き出されていた（`175 * 1.5 = 262.5`。
MuseScoreの`♩=♩.`のようなテンポの読み替え機能によるものと見られる）。これは滑らかな速度変化の
曲線ではなく、離散的な（段階的な）テンポ変化の近似だが、`renderToTimemap()`はこれを正しく
発音時刻の計算に反映する。

**方針**：`rit.`のような自由テキストの内容そのものは使わない（信頼できないため）。MuseScore側で
`<sound tempo>`が併記されていれば、そのぶんはタイムマップの計算に自動的に反映される。テンポ記号が
無い区間の速度変化は、前後の音符を結ぶ直線で近似されることになるが、issue #139のコメントにある
実測（音源に合わせた2曲でのズレが最後まで0.3〜1秒程度に収まった）から、実用上許容できると判断した。

## 実データでの動作確認

実際の楽譜（121小節）で `note_events()` を実行し、438個の音符・和音の点が得られた。時刻・x座標が
ともに単調増加していること、総演奏時間（約133秒）が曲の長さとして妥当であることを確認した。
処理時間は0.2秒未満だった。
