# 2026-09-21 フォント名の Unicode 正規化の検証記録

macOS で、日本語名のフォントが見つからない・見つかっても別のフォントで描かれる件の実測。

## 環境

- WSL2 上の Ubuntu 24.04、ffmpeg 6.1.1（libass 0.17.1）
- 報告は macOS（フォント名は `ls` などからコピー）

## 名前が NFD になる

- macOS で名前をコピーすると NFD（例: 「ギ」が キ ＋ 濁点）になることがある。フォントファイルの name テーブルの名前は NFC
- そのため `casefold()` だけで比べる索引では一致せず、`check` が「フォントが見つかりません」になった
- 対応: 索引を作るときと引くときの両方で `unicodedata.normalize("NFC", name).casefold()` を使う（`fonts.match_key`）

## libass は正規化しない

NFC の名前（`テストゴシック`）を持つフォントだけを `fontsdir` に渡し、.ass のスタイルのフォント名を変えて 320x180 の1フレームを描画し、平均輝度（signalstats の YAVG）を比べた。フォントの `A` は塗りつぶしの四角なので、代替フォントで描かれると値が下がる。

| .ass のフォント名 | YAVG |
|---|---|
| NFC（フォントと同じ） | 55.88 |
| NFD | 29.66 |
| 存在しない名前 | 29.66 |

- NFD の結果は「存在しない名前」と同じ＝libass は名前をそのまま比べており、正規化しない
- 索引だけを直すと、`check` は通るのに描画は代替フォントになる（気づけない）
- 対応: 書き出しに使う .ass（`build/.work/`）を作るときに、スタイルと `\fn` のフォント名を NFC に揃える（`subs.compose`）。利用者の元の .ass は変えない
- 未確認: フォント側の name テーブルが NFD の場合。その場合は索引では引けるが、libass では一致しない可能性がある
