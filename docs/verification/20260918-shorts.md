# 2026-09-18 ショートの書き出し（shorts）

縦型のショート（issue #22）の4段目、`utavideo shorts` の前提にした実測の記録。
縦の版は `build/shorts/<name>.mp4`、16:9 版は `build/shorts/wide/<name>.mp4`。

## 環境

- ffmpeg 6.1.1（Ubuntu 24.04 のパッケージ、libass 付き）。WSL2 で実行
- pysubs2 1.9.0
- 確かめ方: 1280x720・30fps の曲フォルダ（背景は 3 秒の mp4 を繰り返す、音源は 40 秒の wav）を作り、
  `crf = 0`（可逆）で `build` と `shorts` を実行して、映像のフレームの md5（`-f framemd5`）を比べた。
  区間は `0:00:11.51`〜`0:00:27.33`（フレームに丸めると 345〜820 フレーム）で、背景の2周目以降にかかる

## wide のフレームは本編と一致する

| 比べたもの | 結果 |
|---|---|
| `build/shorts/wide/<name>.mp4` の全 475 フレーム と `build/main.mp4` の 345〜819 フレーム | すべて一致 |
| 同じものを 1 フレームずらして比べる | 一致しない（偶然の一致ではない） |

- `build/main.mp4` と同じフィルタの、背景の直後に `fps={fps},trim=start_pts=S:end_pts=E` を入れ、
  字幕の後に `setpts=PTS-STARTPTS` を置いた
- `fps` の出力の時間の単位は `1/fps` なので、`trim` の `start_pts`・`end_pts` はフレームの番号そのものになる
- 入力側の `-ss` は使わない（`-stream_loop` の2周目以降で本編とコマがずれる。issue #22 の実測）

## 縦の版は .ass の時刻をずらさない

`build/.work/shorts/<name>.ass`（区間に入る行を、時刻をずらさずに書いたもの）を使って、次の2つを比べた。

| 比べたもの | 結果 |
|---|---|
| 区間を切り出した `build/shorts/<name>.mp4` の全 475 フレーム と、同じ .ass を曲の頭から曲全体に描いた動画の 345〜819 フレーム | すべて一致 |

区間の頭（11.5 秒）をまたぐ行を、黒い背景に描いて測った。行は本編の
`\move(100,200,900,200)`（9.5〜13.5 秒）と `\fad(2000,2000)`（9.8〜14.0 秒）を、縦（720x1280）に変換したもの。

| 描き方 | 区間の頭の `\move` の位置 | 区間の頭の `\fad` の明るさ | 区間の頭 ＋ 0.5 秒の `\move` | 同じく `\fad` |
|---|---|---|---|---|
| 元の時刻のまま描いて `setpts` で戻す（実装） | 中心 x = 281.5（本編と同じ 281.25） | 218 / 255（残り 0.3 秒で、フェードインの 85 %） | 中心 x = 337.5（本編と同じ） | 255 / 255 |
| .ass を区間の頭へずらす | 何も描かれない（`\fad` が 0 から始まる） | 0 / 255 | 中心 x = 169.5 | 67 / 255 |

- `\move` の位置は、本編（1280x720）の 12.0 秒の x = 600 を幅の比（720/1280）で縮めた 337.5 と一致する
- ずらす方式では、区間の頭をまたぐ行の開始が 0 秒に切り詰められ（pysubs2 の `shift` は負の時刻を 0 にする）、
  `\move`・`\fad` が本編と違う状態で描かれる

## 音声の切り出しとフェード

音源（48kHz・モノラルの wav）の 345〜820 フレーム（11.5〜27.333… 秒）を切り出して比べた。

| 比べたもの | 結果 |
|---|---|
| `atrim=start=S:end=E,asetpts=PTS-STARTPTS` の出力（s16le）の md5 と、音源全体の同じ範囲のサンプルの md5 | 一致（760,000 サンプル） |

`vertical.audio_fade_ms` を変えて書き出し、区間の端の音量を測った（`volumedetect`）。

| `audio_fade_ms` | 頭 0.1 秒の平均 | 末尾 0.2 秒の平均 |
|---|---|---|
| `[0, 0]` | -28.8 dB | -28.7 dB |
| `[300, 1000]`（既定値） | -43.9 dB | -46.7 dB |
| `[1000, 3000]` | -54.5 dB | -56.3 dB |

- 出力の長さは映像・音声とも 15.833… 秒（475 フレーム ÷ 30 fps）で、縦の版と 16:9 版で同じ
- フェードインの間は音が小さいので、区間の頭は歌い出しの少し前に置く（docs/workflow.md）

## 投稿先の長さの上限

2026-09-18 に確かめた。区間の長さ（`E - S`）で判定し、超えたら警告する。

| 投稿先 | 上限 | 出典 |
|---|---|---|
| YouTube のショート | 3 分（180 秒） | [YouTube ヘルプ「Shorts のアップロード」](https://support.google.com/youtube/answer/15424877)：2024-10-15 以降にアップロードした、正方形か縦長で 3 分までの動画がショートとして扱われる |
| X（Premium でない通常のアカウント） | 140 秒（2 分 20 秒） | [X ヘルプ「About longer videos for X Premium subscribers」](https://help.x.com/en/using-x/premium-longer-videos)：Premium でなければ 140 秒まで（ページ本体は 403 で取得できず、検索結果に出る同ページの抜粋で確認した） |

- 上限は投稿先の都合で変わる。`utavideo` は警告だけで、書き出しは止めない
- AAC の書き出しで出力はわずかに長くなることがあるので、判定は出力ではなく区間の長さで行う

## blur の画面（5段目）

`vertical.layout = "blur"` の画面を、別の曲フォルダで確かめた。1920x1080・30fps の背景（動画）と
1080x1920 の縦の設定で、区間を 1〜7 秒にして `utavideo shorts` を実行した。
本編の .ass には、画面いっぱいを不透明な緑で塗る行（`\p1` の図形）を足し、
出力の画素の色から本編の映像の位置を測った。

| `frame_y` | 本編の映像の行（1920 行のうち） | 定義どおりの値 `(1920 - 608) × frame_y` |
|---|---|---|
| `0` | 0〜607 | 0 |
| `0.5` | 656〜1263 | 656 |
| `1` | 1312〜1919 | 1312 |

- 本編の高さは 608（`1080 × 1080 / 1920 = 607.5` を `scale=1080:-2` で偶数にしたもの）
- 上下の帯には、本編に描いた緑が **1 画素も無い**（3 つとも）。帯は背景だけから作られている
- 帯の上には縦用 .ass の `Vertical` で始まるスタイルの行だけが描かれ、本編の歌詞・曲名表示は
  真ん中の映像の中にだけ入る

## 帯のぼかし方

1920x1080 の動画（10 秒）を 1080x1920 の blur の画面にするときの、ぼかしのフィルタだけを比べた
（`-f null -` でエンコードを外し、5 回の最小。20 スレッド）。

| ぼかし | 時間 | 見え方 |
|---|---|---|
| 無し（`null`） | 3.1 秒 | 背景がそのまま見え、帯として落ち着かない |
| `gblur=sigma=40` | 3.3 秒 | 十分にぼける |
| 1/4 に縮めて `gblur=sigma=10` → 元の大きさに戻す（実装） | 2.2 秒 | `gblur=sigma=40` とほぼ同じ（PSNR 43.1 dB。並べても違いが分からない） |
| `boxblur=40:2` | 7.1 秒 | ぼけるが遅い |

**1/4 に縮めてから掛ける方法にした。** 見え方は `gblur=sigma=40` と変わらず、いちばん速い。
縮めるときの `area`（画素の平均）で背景の細かい模様が落ちるので、帯がちらつきにくい。
戻すときは `bilinear` にする（`lanczos` は輪郭を立てるので、ぼかした絵には向かない）。

ぼかしの強さは幅に比例させ（1080 幅で `sigma=40` 相当）、`vertical.size` を変えても同じ見え方にする。
強さの設定項目は足していない。目的は「帯が落ち着いて見える」ことで、この強さなら背景の柄が
文字の読みやすさに影響しなかったため。
